# پایش و مانیتورینگ (Monitoring)

**وضعیت:** فاز ۱۳ — سخت‌سازی، مقیاس و استقرار پایدار
**تاریخ:** مهر ۱۴۰۵

در این فاز پایش با حداقل ابزار (بدون وابستگی سنگین) تعریف می‌شود: Health Check، لاگ و
برخی شاخص‌های عملیاتی که از DB قابل استخراج‌اند.

---

## ۱. سطوح پایش

| سطح | ابزار | فرکانس |
| --- | ----- | ------ |
| زنده‌بودن نمونه | `GET /api/health` (DB up + uptime) | هر ۳۰-۶۰ ثانیه از پایش/Orchestrator |
| لاگ اجرا | `src/lib/logger.ts` → console → جمع‌آوری Docker/systemd | پیوسته |
| خطاهای API | خروجی `jsonError` با کدهای خطا | بررسی دوره‌ای |
| شاخص‌های محصول | کوئری‌های DB (جدول ۲) | روزانه/هفتگی |
| امنیت | Audit Log + ModerationDecision | در رخدادها |

## ۲. شاخص‌های عملیاتی (از DB)

| شاخص | کوئری تقریبی | هدف |
| ---- | ------------ | --- |
| کاربران فعال روزانه | `User.createdAt` در ۲۴ ساعت | روند |
| مسائل بدون پاسخ | `Problem.status = open AND answers none` | سلامت حلقه دانش |
| گزارش‌های باز | `ContentReport.status = pending` | SLA < ۲۴ ساعت |
| خطاهای 5xx | لاگ/پایش | آپ‌تایم |
| حجم Audit | `AuditLog.createdAt` | سلامت ممیزی |

## ۳. لاگ‌ها

- ساختار: `[LEVEL] [scope] message` + متا (اختیاری) از `src/lib/logger.ts`.
- در Production لاگ به stdout می‌رود؛ توسط Docker/systemd جمع‌آوری می‌شود.
- لاگ‌ها نباید داده بیمار/شناسه شخصی ثبت کنند (اصول حریم خصوصی).

## ۴. هشدار (Alerting)

در این فاز هشدار دستی است (بدون ابزار خارجی):

- اگر `/api/health` پاسخ نداد → بررسی نمونه/Rollback (راهنمای استقرار).
- اگر صف گزارش‌ها > آستانه → رسیدگی (SLA ۲۴ ساعت).
- اگر نرخ خطای 5xx بالا رفت → بررسی لاگ.

پس از انتخاب زیرساخت (مثلاً Prometheus + Alertmanager یا سرویس‌های مانیتورینگ) این بخش
به‌صورت واقعی متصل می‌شود؛ معماری فعلی از Health Check استاندارد پشتیبانی می‌کند.

## ۵. Core Web Vitals و عملکرد

- اهداف: LCP < ۲.۵s، INP < ۲۰۰ms، CLS < ۰.۱ در اینترنت متوسط موبایل.
- Bundle/Lazy Loading و Cache در `docs/current-architecture.md` و گزارش فاز ۱۳ مستند شده‌اند.
- پیشنهاد: اندازه‌گیری واقعی با Lighthouse/CrUX پس از استقرار Production.
